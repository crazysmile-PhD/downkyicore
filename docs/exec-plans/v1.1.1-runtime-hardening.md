# Runtime Hardening — Remaining Runtime Semantics

> Revalidated against current `main` on 2026-09-25.
>
> This file is no longer a v1.1.1 implementation checklist. The v1.1.1 integrated
> invariants are historical completed work and are intentionally omitted here.
> This document keeps only runtime semantics that still have a current code gap.

## Scope

The remaining work is narrow:

- do not redesign the download architecture;
- do not add a second retry owner, reservation registry, or backend-specific workflow;
- preserve settings, SQLite history, unfinished tasks, transfer-file identity,
  aria2 GID/resume state, and the existing pipeline commit boundary;
- implement each item as a semantic correction against the current owner.

## Remaining Semantics

### 1. Transfer Integrity Must Participate In The Coordinator Retry Loop

Current gap:

- Built-in transfer performs file-integrity checking before returning success, so
  invalid media can return `DownloadTransferFailureKind.InvalidMedia` to
  `DownloadTransferCoordinator`.
- aria2 can report backend success before the shared media-file integrity check
  runs. `DownloadMediaStage` may therefore discover an invalid file only after
  the coordinator has already returned success.
- The existing retry policy can move `InvalidMedia` to a backup address, but
  invalid output discovered outside the coordinator cannot use that transition.
- After backup addresses are exhausted, invalid-media recovery does not currently
  receive the same one-bounded playback-address refresh opportunity as an expired
  address.

Required invariant:

- Backend completion is not transfer success until the produced file passes the
  transfer-integrity contract.
- Integrity classification belongs inside the coordinator-owned attempt lifecycle,
  independent of whether the backend is built-in or aria2.
- Invalid output may try remaining backup addresses and at most one bounded
  playback-address refresh within the existing global attempt budget.
- A source change still requires the existing reset -> physical cleanup -> durable
  backend-identity clear transition before the replacement source is contacted.
- Do not create backend-specific retry semantics.

Previously rejected approaches:

- Do **not** restore the former aria2 error-code-1 special case.
- Do **not** restore a fixed global retry expansion.
- PR #120 intentionally removed both approaches. The remaining requirement is to
  put integrity evidence into the existing coordinator/retry semantics, not to
  recreate either rejected policy.

### 2. Duration Validation Must Use Expected Media Time As Authority

Current gap:

- `FfmpegMediaValidator.IsDurationClose` currently allows
  `max(3 seconds, expected * 5%)`, so the accepted absolute error grows without
  a fixed upper bound as media duration increases.
- Tail seek positions are currently derived from the already-produced actual
  duration. A truncated output can therefore move its own "tail" validation point
  earlier.

Required invariant:

- Duration tolerance is derived from expected duration and must have a fixed upper
  bound; long media must not gain an arbitrarily large accepted missing tail.
- The expected duration is the authority for deciding whether output is complete.
- Expected-tail validation points must be derived from expected duration, not from
  a shortened actual duration.
- If the output cannot reach an expected validation point, validation fails rather
  than silently moving the point earlier.

Decision history:

- No explicit rejection was found. This item was deferred from the v1.1.1
  integration scope and remains valid after revalidation.

### 3. Required Audio Must Be Proven, Not Inferred From File Existence

Current gap:

- Media validation currently proves a video stream, duration, and middle/tail
  video decode for concat output.
- `ValidateStage` primarily proves that finalized output exists; it does not prove
  that a task requesting audio actually received a usable audio stream.
- A requested audio+video output therefore lacks one final semantic proof:
  required audio presence, decodability, and bounded audio/video duration drift.

Required invariant:

- `RequestedContent` is the authority for required output streams.
- If `NeedsVideo` is true, finalized media must contain usable video.
- If `NeedsAudio` is true, finalized media must contain usable audio.
- Required streams must remain decodable near the expected tail.
- When both audio and video are required, their durations must remain within a
  bounded drift contract.
- Audio-only output must not fail merely because it has no video stream.

Decision history:

- No explicit rejection was found. This item was deferred, not rejected.

### 4. Exact Content Length Must Be Checked In Both Directions

Current gap:

- `DownloadFileIntegrity` rejects a file when the actual length is smaller than
  the available expected/total length.
- It does not reject an oversized file.
- The current `ExpectedSize` value must not be silently reinterpreted as exact
  unless its source contract actually guarantees an exact content length.

Required invariant:

- Preserve the distinction between an approximate/unknown size and an
  authoritative exact content length.
- When exact length is reliably known, successful transfer requires
  `actualBytes == exactBytes`.
- Both undersized and oversized outputs fail the integrity contract.
- When exactness is not guaranteed, do not manufacture an equality requirement
  from an estimate.

Decision history:

- No explicit rejection was found. This item was deferred, not rejected.

### 5. DURL Must Honor The Same Requested-Content Semantics As DASH

Current gap:

- DASH flow already branches on `NeedsAudio` and `NeedsVideo`.
- DURL flow downloads the DURL media segments whenever any media is requested and
  currently finalizes them through the DURL MP4 path.
- As a result, input transport format can override user output intent.

Required invariant:

- `RequestedContent`, not DASH/DURL transport format, defines the requested
  output.
- DURL video+audio, video-only, audio-only, and configured audio transcoding must
  have the same user-visible meaning as the equivalent DASH selections.
- DASH and DURL may keep different internal implementations; they must not expose
  different selection semantics.

Decision history:

- No explicit rejection was found. This item was deferred, not rejected.

### 6. Validate DURL Manifest Semantics Before Starting Transfer

Current gap:

- DURL inputs are sorted by `DURL.Order`, and stable transfer identity uses that
  order.
- Sorting does not prove that the manifest itself is valid.
- Current transfer entry does not reject duplicate or non-positive order values
  before segment downloads begin.

Required invariant:

- Validate the complete DURL manifest before starting any segment transfer.
- Reject duplicate `Order` values.
- Reject non-positive `Order` values.
- Reject malformed segment descriptors required for deterministic transfer
  identity or source selection.
- Sorting remains deterministic ordering after validation; it is not validation
  itself.
- Do not add a second mutable manifest registry.

Decision history:

- No explicit rejection was found. Existing tests already treat `DURL.Order` as
  stable identity, so this tightens the existing contract rather than replacing
  it.

## Verification

Each semantic item requires:

- a regression that fails on the current behavior before the fix;
- strict Release build with warnings as errors;
- all affected test projects;
- architecture/review gates already owned by the repository;
- `git diff --check`.

Backend behavior must be proven at the shared semantic boundary. Mock-only tests
must not be used to claim real Downloader, aria2, FFmpeg, or ffprobe behavior when
an existing real-runtime suite owns that claim.

## Rollback

Revert one semantic item at a time. A rollback must not delete user databases,
completed history, partial files, settings, transfer identities, or resume state.
