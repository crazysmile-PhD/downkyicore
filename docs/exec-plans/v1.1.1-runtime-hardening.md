# v1.1.1 Runtime Hardening

## Goal

Prevent corrupt, conflicting, or unrecoverable download state from becoming a
completed output while preserving settings, SQLite download history, unfinished
tasks, and resumable transfer state.

## Integrated Release Invariants

### 1. Durable Output Path Ownership

Ownership:

- `DownloadTaskAdmissionService` is the only admission coordinator. It probes
  candidates through the existing Application/store boundary, then persists the
  selected task before publishing its UI projection or queue identity.
- `DownloadOutputPathResolver` owns candidate generation and on-disk collision
  checks. It does not maintain a mutable reservation registry.
- SQLite schema v3 derives `output_reservation_key` from the persisted
  `DownloadOutput.BasePath`. Task insertion claims the key in the same transaction,
  and a partial unique index rejects check-then-insert races.
- Queued, Downloading, Pausing, Paused, Failed, and Canceled tasks retain the
  reservation. Completed releases it in the completion transaction; Canceled
  releases it only after cleanup succeeds and the task commits Deleted.
- Output keys are ordinal-ignore-case on Windows and macOS and ordinal on Linux.
  Disabling automatic numeric suffixing makes a collision fail closed.
- Download-owned FFmpeg merge and concat use `overwriteDestination: false`; a
  foreign destination cannot be replaced or deleted.

Executable evidence:

- `DownloadTaskAdmissionServiceTests`
- `SqliteDownloadTaskStoreTests`
- `FfmpegConcatRuntimeTests`
- `DownloadRuntimeArchitectureTests`

### 2. Typed Mux Failure And Recovery

Ownership:

- `FfmpegProcessor` and `FfmpegConcatRuntime` return typed operation and input
  failures. Missing input, inaccessible input, unavailable runtime, timeout,
  process failure, destination conflict, output I/O, and confirmed decode
  corruption retain distinct semantics.
- Only positive decode-corruption evidence may classify a source as invalid.
  Infrastructure, permission, destination, and runtime failures preserve source
  files, completed keys, and resume identity.
- Ordinary merge and multi-segment DURL concat share `FfmpegInputDiagnostic`.
  DURL diagnosis checks each segment and reports only the corrupt paths.
- Normal FFmpeg work, validation, and failure diagnostics use the singleton
  processor's existing `FfmpegMaxParallelJobs` gate.
- `DownloadTransferFileCleanup` is the only physical invalid-source cleanup owner.
  `DownloadTaskApplicationService.InvalidateCompletedFilesAsync` mutates durable
  completed keys and backend identity only for paths whose cleanup succeeded.
- Required artifacts and media remain operation-owned until the pipeline commits
  Completed. Before that commit, every created file must be durably claimed or
  removed; successful mux alone cannot delete reusable source inputs.

Executable evidence:

- `FfmpegProcessorMergeTests`
- `FfmpegConcatRuntimeTests`
- `MuxFailureRecoveryTests`
- `DownloadPipelineCommitBoundaryTests`
- `DownloadTaskApplicationServiceTests`

### 3. Clean Restart When Transfer Source Changes

Ownership:

- `DownloadTransferCoordinator` remains the only retry-budget, address-selection,
  and playback-address-refresh owner.
- Built-in and aria2 resume behavior remains valid for the identical source.
  Selecting a different URL requires the backend owner to stop/remove its old
  operation and the shared cleanup owner to remove the target plus `.aria2` and
  `.download` state before the new source is contacted.
- Durable backend identity is cleared only after backend reset and physical cleanup
  succeed. Reset or cleanup failure stops the transition and cannot contact the
  replacement source.
- Returning the same normalized URL from refresh preserves partial state and
  backend identity.
- aria2 reset RPC calls propagate cancellation and use a bounded timeout. Built-in
  reset is a no-op because it has no separate backend identity owner.

Executable evidence:

- `DownloadRetryPolicyTests`
- `AriaClientRpcContractTests`
- `Aria2TlsIntegrationTests`
- `Aria2TlsRedirectIntegrationTests`

### 4. Cancellation Keeps Its Owning Semantics

Ownership:

- `DownloadPipeline` absorbs `OperationCanceledException` only when its owning
  execution token is canceled.
- `DownloadOrchestrator` separately recognizes shutdown and per-task
  cancellation. If cancellation is observed while both owners remain active, it
  records a retryable failure through the existing executor/state writer and
  keeps the worker alive.
- `TryMarkFailedAsync` checks current durable phase before mutation, so a task
  already moved to Pausing, Paused, Canceled, Deleted, or Completed cannot be
  converted into a synthetic failure.

Executable evidence:

- `DownloadOrchestratorTests.UnexpectedCancellationFailsTaskWithoutStoppingWorker`
- `DownloadOrchestratorTests.CancelingOneActiveTaskDoesNotStopTheWorker`
- `DownloadOrchestratorTests.ShutdownRecoversActiveTaskToQueuedState`

## Remaining Deferred Runtime Items

These items are not implemented by the integration work above. Revalidate each
against current `main` before starting a separate work item.

5. Move transfer integrity into the coordinator retry loop so invalid aria2 or
   built-in output can try backup addresses and one bounded playback-address
   refresh.
6. Use a fixed upper bound and a small percentage for duration tolerance; expected
   tail validation must not depend on an already shortened actual duration.
7. Require and validate audio when the selected output requires it, including tail
   decode and bounded audio/video duration drift.
8. Reject undersized and oversized files when a reliable exact content length is
   available.
9. Add deterministic fail-on-error and multi-point or segment-boundary validation
   without turning normal PR verification into an unstable benchmark.
10. Make DURL output honor video-only, audio-only, and transcoding selections.
11. Keep no-resource subtitle/cover outcomes distinct from API, conversion, write,
    permission, and zero-byte failures; required NFO output follows the same
    active-pipeline contract.
12. Reject duplicate, non-positive, and malformed DURL order manifests before
    transfer.

## Verification

Every implemented item requires a regression that fails on the old behavior,
strict Release build, all affected test projects, architecture gates, and
`git diff --check`. Cross-platform or real-binary claims require their existing
runtime suites; mocked tests alone cannot prove Downloader, aria2, or FFmpeg
behavior.

## Rollback

Revert one semantic item at a time. Never roll back by deleting user databases,
completed history, partial files, or settings. A rollback restores the previous
code path together with its corresponding tests.
