# v1.1.1 Runtime Hardening

## Goal

Prevent corrupt, conflicting or unrecoverable download state from becoming a completed output.
Each numbered item is implemented in priority order on a dedicated branch after PR #120 scope
cleanup. Existing domain state, SQLite resume data and user settings remain compatible.

## Active Work: P0 Item 2 (PR #127, Integration Pending)

Owner and overlap audit:

- `DownloadTaskApplicationService.InvalidateCompletedFileAsync()` remains the only durable owner
  for completed-key revocation. It now clears the single backend identity in the same persisted
  mutation; no second reset service or database representation was added.
- `DownloadTransferFileCleanup` remains the only physical owner for deleting an invalid source
  and its `.aria2` / `.download` sidecars.
- `DownloadMediaStage` records the existing transfer key beside each resolved audio, video or
  DURL file in `DownloadExecutionContext`; `MuxStage` does not reconstruct keys from paths.
- `FfmpegProcessor` remains the single FFmpeg process/concurrency owner. Its typed mux result
  reports only inputs whose fail-on-error stderr contains positive decode-corruption evidence.
  Process startup failure, timeout, permission/runtime failure, destination conflict and
  finalization errors do not accuse source media.
- Ordinary merge and multi-segment DURL concat use the same input-diagnostic owner. DURL failure
  validates each non-empty segment independently and reports only the segment paths that are
  positively identified as corrupt.
- Mux, concat, output validation and failure diagnostics share the same `FfmpegMaxParallelJobs`
  gate; failure analysis cannot create a second concurrency budget.

Root-cause review escalation:

- The later destination-finalization, inaccessible-input and cleanup findings belong to the same
  failure family as the earlier infrastructure/corruption review. The shared defect is semantic
  compression: `RunToFileAsync` returns `bool`, input preflight relies on `File.Exists`, and
  cleanup returns `void`, so `MuxStage` cannot know whether destructive invalidation is legal.
- The fix must strengthen the existing FFmpeg result, input-diagnostic, cleanup and Application
  mutation owners. Do not add caller-specific `if` branches, a second cleanup service, a second
  FFmpeg limiter or a second durable cache representation.
- Investigation may inspect sibling paths, but only the same cleanup/invalidation family in
  `DownloadMediaStage`, `DownloadTransferCoordinator` and `MuxStage` is in scope. Unrelated media
  validation, output reservation, retry policy and pipeline ordering remain separate PR work.

Failure and transition matrix:

| Failure kind | Physical source/sidecar | Completed keys/backend identity | Retry outcome |
| --- | --- | --- | --- |
| missing or zero-byte source | clean exact source set | revoke matching keys atomically after cleanup | redownload source |
| positively confirmed decode corruption | clean exact source set | revoke matching keys atomically after cleanup | redownload source |
| inaccessible input or unsupported filesystem object | preserve | preserve | infrastructure failure |
| FFmpeg missing/runtime/process-start failure | preserve | preserve | infrastructure failure |
| timeout without caller cancellation | preserve | preserve | typed timeout failure |
| destination exists, permission denied or output-finalization IO | preserve; foreign output untouched | preserve | destination failure, no input diagnosis |
| output validation/process failure with confirmed corrupt inputs | clean only confirmed inputs | one durable batch revokes only matching keys | redownload invalid sources |
| output validation/process failure without corruption evidence | preserve | preserve | infrastructure/validation failure |
| invalid-source cleanup failure | preserve the failed source and remaining sidecars | preserve that source's completed key; batch-revoke only successfully cleaned siblings | fail closed; retry after cleanup becomes possible |
| cleanup succeeds but durable invalidation fails | invalid source may be absent | durable state remains authoritative | next media preflight repairs; failure remains visible |
| caller cancellation | preserve | preserve | cancellation propagates, no retry/failure conversion |

Acceptance:

- a failed DASH mux can identify audio, video or both invalid inputs;
- only matching invalid sources lose their completed key, file, sidecars and backend identity;
- valid sibling sources remain reusable by the next retry;
- infrastructure-only mux failure preserves every source, completed key and resume identity;
- valid/corrupt/valid DURL input invalidates only the corrupt segment;
- diagnostic FFmpeg processes cannot exceed the configured FFmpeg concurrency budget;
- FFmpeg operation results retain destination, process, timeout, input-access and confirmed-input
  failure kinds instead of reducing them to `bool` or an untyped path list;
- cleanup must succeed for each source before its durable completed key is revoked; successfully
  cleaned siblings are removed in one Application mutation while failed sources remain durable;
- every sibling caller of invalid-artifact cleanup fails closed when physical cleanup is
  incomplete;
- cancellation continues to propagate and no settings, SQLite schema or task data format changes.

## P0: Data Ownership

1. Reserve normalized output paths atomically before task persistence. Compare active queued,
   downloading, paused, failed and canceled tasks. SQLite schema v3 owns an indexed durable
   reservation key that is claimed in the task insertion transaction and protected by a partial
   unique index; admission must not reload all unfinished tasks or maintain a mutable registry.
   Use case-insensitive keys on Windows and macOS, and reject collisions when automatic numeric
   suffixing is disabled. Release a canceled task's claim only after cleanup commits Deleted.
   FFmpeg finalization may not overwrite a destination owned by another task.
2. Distinguish invalid video/audio source from mux infrastructure failure. Invalid source revokes
   only its completed key, partial/sidecar and backend identity so retry downloads that source;
   missing FFmpeg or destination permission must preserve valid source files.

## P1: Retry And Validation Placement

3. A host/URL change may resume only with verified matching identity, range and total length;
   otherwise delete partial state and restart from byte zero.
4. Swallow cancellation only when the owning token is canceled. Unexpected task cancellation is
   a typed retryable failure and cannot leave a durable task in Downloading.
5. Transfer integrity belongs inside the coordinator retry loop. Invalid output can try a backup
   URL and one bounded playback-address refresh before final failure.
6. Duration tolerance uses a fixed upper bound and a small percentage, and expected-tail decode is
   independent of a shortened actual duration.
7. Validation accepts explicit required-stream flags; audio-required output must contain decodable
   audio through the tail with bounded audio/video duration drift.

## P2: Defensive Completeness

8. Reliable exact content length rejects both undersized and oversized files.
9. FFmpeg fail-on-error and deterministic multi-point/segment-boundary checks cover local damage.
10. DURL honors video-only/audio-only and transcoding choices.
11. No-resource outcomes for subtitles/covers are separate from API, conversion, write, permission
    and zero-byte failures. Required NFO output follows the same active-pipeline contract.
12. Reject duplicate, non-positive and malformed DURL order manifests before transfer.

## Verification

Every item requires a test that fails on the old behavior, strict Release build, all affected test
projects, architecture gates and `git diff --check`. Cross-platform or real-binary claims require
their existing runtime suites; no item may be marked complete from a mocked unit test alone when
the contract concerns Downloader, aria2 or FFmpeg behavior.

## Rollback

Revert one semantic item at a time. Never roll back by deleting user databases, completed history,
partial files or settings. A rollback must restore the previous code path and its corresponding tests.
