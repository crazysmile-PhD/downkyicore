# v1.1.1 Runtime Hardening

## Goal

Prevent corrupt, conflicting or unrecoverable download state from becoming a completed output.
Each numbered item is implemented in priority order on a dedicated branch after PR #120 scope
cleanup. Existing domain state, SQLite resume data and user settings remain compatible.

## Prior Work: P0 Item 1 (Integration Pending)

Owner and overlap audit:

- `DownloadTaskAdmissionService` remains the only task-admission owner. It serializes the
  authoritative unfinished-task query, path selection and first persistence write.
- `IDownloadTaskApplicationService.GetUnfinishedAsync()` remains the source of truth; the mutable
  `DownloadListState` projection is not used to decide ownership.
- `DownloadTaskDraftFactory` already owns disk-collision suffix behavior. That logic moves into one
  shared pure path resolver and is extended for active reservations; no parallel validator or
  output-path registry is introduced.
- Existing `DownloadOutput.BasePath` persistence is sufficient. This item adds no database table,
  schema migration, settings field or user-data rewrite.
- Queued, Downloading, Pausing, Paused and Failed tasks retain ownership because Failed tasks are
  retryable. Completed, Canceled and Deleted tasks do not reserve an active runtime path.

Acceptance:

- concurrent admissions cannot persist the same normalized output base path;
- Windows comparison is ordinal and case-insensitive, while other platforms remain ordinal;
- suffix selection skips both active reservations and existing output files;
- the reservation is durable before UI projection and queue publication;
- final download mux/concat refuses to overwrite a pre-existing destination.

## Active Work: P1 Item 3

Owner and overlap audit:

- `DownloadTransferCoordinator` remains the only owner of retry budgets, address selection and
  playback-address refresh. Source-transition behavior is added there instead of introducing a
  backend-local retry policy.
- `DownloadTransferFileCleanup` remains the only physical owner for deleting the target and its
  `.aria2` / `.download` resume sidecars. It must report whether cleanup actually completed so a
  source switch can fail closed.
- `BuiltinTransferBackend` deliberately enables Downloader auto-resume and `Aria2TransferBackend`
  deliberately enables aria2 continuation. Both remain valid for the identical source; neither may
  inherit partial state after the coordinator selects a different URL.
- Downloader 5.9.0 persists total length and chunk state in its `.download` package but not the
  source URL or an ETag validator. Equal length therefore cannot prove that a primary and backup
  CDN represent a compatible resumable source.
- No database schema, settings field, raw URL log, second retry owner or second cleanup service is
  introduced. Existing unfinished-task and same-address resume compatibility remains intact.

Acceptance:

- retrying the exact same normalized URL preserves partial state and backend identity;
- selecting a different primary/backup URL clears the target, both resume sidecars and backend
  identity before the next backend invocation;
- refreshed addresses receive the same treatment when the selected source differs;
- a failed cleanup stops before the new source is contacted and returns a typed disk failure;
- deterministic coordinator tests and a real Downloader range fixture prove the replacement source
  starts at byte zero instead of appending to or resuming from the previous CDN;
- cancellation semantics and all persisted user/download data formats remain unchanged.

## P0: Data Ownership

1. Reserve normalized output paths atomically before task persistence. Compare active queued,
   downloading and paused tasks; use `OrdinalIgnoreCase` on Windows. FFmpeg finalization may not
   overwrite a destination owned by another task.
2. Distinguish invalid video/audio source from mux infrastructure failure. Invalid source revokes
   only its completed key, partial/sidecar and backend identity so retry downloads that source;
   missing FFmpeg or destination permission must preserve valid source files.

## P1: Retry And Validation Placement

3. A host/URL change may resume only with verified matching identity, range and total length;
   otherwise delete partial state and restart from byte zero.
4. Swallow cancellation only when the owning token is canceled. Unexpected task cancellation is
   a typed retryable failure and cannot leave a durable task in Downloading.
5. Transfer integrity belongs inside the coordinator retry loop. Invalid output can try a backup
   URL and one bounded playback-address refresh before final failure.
6. Duration tolerance uses a fixed upper bound and a small percentage, and expected-tail decode is
   independent of a shortened actual duration.
7. Validation accepts explicit required-stream flags; audio-required output must contain decodable
   audio through the tail with bounded audio/video duration drift.

## P2: Defensive Completeness

8. Reliable exact content length rejects both undersized and oversized files.
9. FFmpeg fail-on-error and deterministic multi-point/segment-boundary checks cover local damage.
10. DURL honors video-only/audio-only and transcoding choices.
11. No-resource outcomes for subtitles/covers are separate from API, conversion, write, permission
    and zero-byte failures. Required NFO output follows the same active-pipeline contract.
12. Reject duplicate, non-positive and malformed DURL order manifests before transfer.

## Verification

Every item requires a test that fails on the old behavior, strict Release build, all affected test
projects, architecture gates and `git diff --check`. Cross-platform or real-binary claims require
their existing runtime suites; no item may be marked complete from a mocked unit test alone when
the contract concerns Downloader, aria2 or FFmpeg behavior.

## Rollback

Revert one semantic item at a time. Never roll back by deleting user databases, completed history,
partial files or settings. A rollback must restore the previous code path and its corresponding tests.
