# DownKyi v1.1.3

v1.1.3 交付目前 `main` 已合併、但仍需要正式版本提供給使用者的登入持久化、
字幕下載安全與 shutdown reliability 修正。

## 使用者可見修正

- QR 登入流程會在同一個隔離 session 中收集 polling、callback 與 redirect
  回應的完整 `Set-Cookie`，原子保存後再由 production path 重新載入，且只有
  `/x/web-interface/nav` 回報 `isLogin=true` 才顯示登入成功。正常關閉並重啟
  應可保留登入狀態；Issue #187 仍等待本版本發布後的使用者現場驗收。
- 修復特定影片字幕地址為 `//host/path` 時，在 Windows 被 .NET URI parser
  誤判為 UNC / `file://`，導致字幕下載失敗或持續卡住的問題。合法的
  protocol-relative URL 現在會在送出 request 前補成 HTTPS。
- 動態字幕 JSON 位址由 Bilibili response 選擇，因此該 request 明確不攜帶
  login Cookie 或 buvid；PlayerV2 metadata request 原有的 authenticated 行為
  保持不變。
- 字幕 URI 驗證只接受具有效 host 的 HTTP / HTTPS，並拒絕 `file:`、`ftp:`、
  `data:` 等 scheme。驗證成功後保留 response 的 opaque URL spelling，
  `%7E`、`%2F` 等 percent-encoded path/query 不會被 parser 改寫。

## Reliability 與發布內容

- unexpected cancellation 與 owned-worker shutdown timeout 不再被誤報為成功；
  test runner routing 與 SQLite pool ownership 已同步加強。
- 發布使用固定版本與 SHA-256 的 FFmpeg mirror；Windows、Linux 與 macOS
  package jobs 會驗證 DownKyi、aria2、FFmpeg、ffprobe、Fluent theme、assembly
  version、publish manifest 與 package sidecar。
- macOS 只允許兩種 trust mode：完整 Apple credentials 時執行 Developer ID、
  notarization、stapling 與 Gatekeeper 驗證；完全沒有 credentials 時使用 ad-hoc
  signing，但仍要求 final App strict codesign、DMG remount、內容與實際啟動驗證。

## 驗證與相容性邊界

- 正式發布只能從完成本版修正與 release metadata 的單一 exact `main` commit
  建立 annotated `v1.1.3` tag；既有 `v1.1.2` tag 與 subject 不會移動。
- 發布前必須通過 strict Release build、完整 test suite、必要 architecture、
  CodeQL、package audit，以及所有 Windows / Linux / macOS package 與 artifact
  gates。
- 保留 settings JSON、資料目錄、portable mode、legacy SQLCipher SQLite、
  未完成任務、aria2 GID、partial file map、completed segment keys 與續傳狀態。
- 發布包不包含開發者 Cookie、帳號資料、Config、Logs、Cache、Storage 或
  下載資料庫。

## Artifact delivery authority

- Windows 與 Linux 每個 RID 只執行一次 `dotnet publish`。該 canonical
  staging payload 先加入實際安裝於 runtime directory 的 `LICENSE`，再由
  `validate-publish-output.ps1` 建立完整 path、byte count 與 SHA-256 manifest；
  Linux 各 package-kind job 從同一份 immutable tar 還原該 RID 的 payload；
  PupNet 1.8.0 使用 standalone mode 將它複製至 `${BUILD_APP_BIN}`，不再自行
  執行第二次 publish。
- `LICENSE` 與 managed/native runtime 同目錄，因此屬於 manifest-owned runtime
  payload。AppImage 的 `AppRun`、desktop/AppStream/icon，以及 deb/rpm control
  與 `/usr/share` metadata 屬於 package wrapper，不冒充 canonical runtime
  manifest 的一部分；其中 release-critical 的 package identity、architecture、
  entrypoint、symlink、permission 與 launch semantics 由 package-kind gates 驗證。
- AppImage 內容以 `--appimage-extract` 觀察，保留 symlink 與 Unix mode；若
  `AppRun` 是 symlink，必須精確指向 `usr/bin/DownKyi`，且 target 必須存在、
  可由 non-owner 執行。`AppRun` 與 `--appimage-extract-and-run` launch smoke
  仍為必要 gate。
- Linux ARM64 在 x64 Ubuntu host cross-publish 與 PupNet cross-package，避開
  ARM64 host-side `Grpc.Tools` protoc crash；candidate 以 tar 傳至 native ARM64
  validator，只有完整 runtime 內每一個 ELF（包含 native `.so`）皆為 aarch64，
  且通過 deb metadata、AppImage 與 launch gates 後才上傳 final release artifact。
